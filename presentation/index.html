Overview

Proof of concept · Android device identity

A client credential that cannot be copied off the device.

The PoC replaces bearer tokens and file-stored client certificates with an EC P-256 key minted inside the device's StrongBox HSM or TrustZone TEE, marked non-exportable. The private key never enters app memory. The backend issues an X.509 client certificate only after it has verified, against Google's hardware attestation roots, that the key really was minted in genuine secure hardware on a verified-boot, locked device — and then authenticates every request with that certificate over mutual TLS 1.3.

Non-exportable key Root, a memory dump, or a Frida hook yields no key material. Signing happens inside the enclave.
Proven provenance The attestation chain proves hardware backing, app binding, boot state and patch level — before any certificate is issued.
Server-owned identity Identity is derived server-side as SHA-256 of the attested public key. A client cannot name itself.
Credential in the handshake Authentication is the TLS handshake itself. No token to replay, intercept, or forward.

What it removes

  • Bearer tokens replayable from any host once exfiltrated
  • Client certificates and keys sitting in app-private files
  • Client-asserted device IDs that are trusted as identity
  • Enrollment that cannot distinguish a real handset from an emulator or a script

What replaces it

  • Hardware-bound key, signature-only, no export path
  • Short-lived CA-issued certificate, 7-day TTL, rotatable
  • Identity = hash of the attested key, bound at issuance and re-checked per request
  • Attestation policy: hardware backing, verified boot, locked bootloader, app package, OS patch level, Google revocation list

Architecture

01 Challenge The device fetches a random nonce, valid 60 s, single use.
02 Keygen A fresh EC key is minted in the enclave with the nonce embedded in its attestation extension.
03 CSR A PKCS#10 request is assembled in the app and signed by the enclave.
04 Attest & issue The server validates the chain and policy, derives identity from the attested key, and signs the certificate.
05 Access Every protected call is a mutual TLS 1.3 handshake the enclave signs live.
03 / 04

Implementation

Android client On the device
KeystoreManager Generates EC secp256r1 under PURPOSE_SIGN with setIsStrongBoxBacked(true), falling back to TEE when StrongBox is absent — detected by walking the whole cause chain, since vendors wrap StrongBoxUnavailableException. The server nonce goes in via setAttestationChallenge().
Alternating key slots A new key is minted into the inactive of two alias slots and promoted only after the server accepts enrollment. A failed or interrupted enrollment never destroys a working identity.
CsrGenerator + signer A Bouncy Castle ContentSigner bridges to SHA256withECDSA over the keystore handle, so the PKCS#10 request is signed inside the enclave with no key material in app memory.
mTLS client A custom X509ExtendedKeyManager supplies the hardware key handle and the issued chain during the handshake; the OkHttp client is pinned to TLS 1.3 only and anchored on the CA returned at enrollment.
Backend service On the server
Attestation verifier Parses the Key Description extension 1.3.6.1.4.1.11129.2.1.17 and chains the leaf to Google's hardware attestation roots. The nonce is read from the extension, never from the request body, and must match an unconsumed challenge.
Policy, enforced strictly Hardware-backed security level (TEE or StrongBox), verified boot and locked bootloader from the TEE-enforced root of trust (tag 704), app package binding (709), minimum OS version and patch level (705/706), and Google's revocation status list — fail-closed. The CSR public key must equal the attested leaf key.
Identity derivation Identity is SHA-256 of the attested SubjectPublicKeyInfo, computed server-side and written into the certificate CN. The client-supplied device_id is a validated display label with no authority. Re-enrolling a revoked key is refused.
Request-time binding A verified handshake is not sufficient. Middleware re-checks that the presented certificate's key fingerprint equals its CN, that the serial is the currently issued one for that identity, and that neither identity nor serial is revoked — so a superseded certificate stops working immediately.
Issuance & listeners An in-process ECDSA P-256 CA signs 7-day client certificates. If the registry write fails, the just-issued serial is revoked so no untracked certificate circulates. Enrollment and protected traffic run as two listeners with independent TLS configuration.
Not yet production The device registry and challenge store are in-memory, and the CA key lives in the service process. Both want durable storage and a real CA or HSM-held signing key.
Trust on first use The mTLS trust anchor is adopted from the enrollment response. Safe because enrollment itself is anchored to system CAs in release builds, but a pinned anchor is stronger.
Renewal path exists Slot alternation plus serial binding already gives clean rotation: enroll again, the new serial becomes current, the old one is rejected on the next request.
Verified by tests 27 backend tests including a full loopback TLS 1.3 handshake and a regression fixture captured from a real device attestation; 6 client tests covering CSR generation and SSL context assembly.

iOS — beyond the PoC

Platform assessment · not implemented

Yes — but the attested key and the certificate key are two different keys.

Every current iPhone has a Secure Enclave, and a key generated in it is as non-exportable as a StrongBox key — that half maps across cleanly, with no hardware fallback branch to write. What iOS has no public API for is attesting an arbitrary Secure Enclave key; WWDC 2026 confirmed that is still the case. App Attest attests its own key and, through it, the app instance. So the identity key that carries the client certificate earns its trust indirectly: App Attest signs an assertion over the CSR.

Control-by-control, Android against iOS
Android control iOS equivalent Verdict
Non-exportable hardware key Secure Enclave via kSecAttrTokenIDSecureEnclave, P-256 only, gated by SecAccessControl. Universal on current hardware — no StrongBox-or-TEE branch to write. Equivalent
Provenance of the enrolled key App Attest attests its own key, never the identity key. The binding is transitive through the assertion, so the identity key's enclave residency is asserted by the app rather than proven by Apple. Indirect
Challenge freshness Server challenge goes in as clientDataHash; the derived nonce is sealed into the attestation leaf and reconstructed server-side. Equivalent
App binding — tag 709 rpIdHash equals SHA-256 of teamID.bundleID. iOS 27 adds bundle version and a launch-environment category, which Android's tag does not carry. Equivalent
Verified boot, locked bootloader — tag 704 Not exposed to apps. Attestation fails on a tampered device, but there is no boot-state field to write policy against. Absent
OS version, patch level — tags 705/706 Not carried in the attestation object. Absent
Google revocation status list The attestation receipt yields a 30-day fraud metric — how many attested keys that device has minted. A risk score to weigh, not a fail-closed verdict. Partial
The two gaps are structural Boot state and patch level simply are not in an App Attest object, and no server-side check recovers them. Policy that depends on either needs device management instead.
Prototype the plumbing first iOS ships no CSR API — the PKCS#10 DER is hand-assembled and signed with SecKeyCreateSignature. And URLCredential(identity:) needs a SecIdentity, which cannot be built directly: the issued certificate is added with SecItemAdd and the keychain pairs it to the enclave key by public-key hash. Apple confirms the workflow but documents nothing enclave-specific, and errSecItemNotFound here is the iOS counterpart of this PoC's keystore2 obstacle.
The handshake is ordinary A URLSessionDelegate challenge on NSURLAuthenticationMethodClientCertificate supplies the identity, with TLS 1.3 pinned through tlsMinimumSupportedProtocolVersion. Network.framework gives finer control where it is needed.
The backend barely moves Challenge issuance, identity derivation from the CSR key, CA signing, the device registry, and the request-time fingerprint and serial binding are all platform-agnostic and stay exactly as built. Only the attestation verifier gains a second implementation, chosen per platform at enrollment.
